# Spec Delta

## Purpose

Задаёт контракт рабочего окружения проекта: воспроизводимую установку, единые команды разработки, сборки и проверки качества, структуру исходников, метаданные репозитория и отслеживание обновлений зависимостей.

## ADDED Requirements

### Requirement: Воспроизводимая установка зависимостей
Проект SHALL фиксировать менеджер пакетов и точные версии зависимостей в репозитории, чтобы установка на чистой машине давала то же дерево зависимостей.

#### Scenario: Установка по lock-файлу
- **WHEN** разработчик клонирует репозиторий и выполняет `pnpm install --frozen-lockfile`
- **THEN** установка завершается с кодом 0 без изменения `pnpm-lock.yaml`

#### Scenario: Менеджер пакетов закреплён
- **WHEN** разработчик открывает `package.json`
- **THEN** поле `packageManager` указывает pnpm с конкретной версией

### Requirement: Локальный сервер разработки
Проект SHALL предоставлять команду `pnpm dev`, которая запускает приложение локально и отдаёт главную страницу.

#### Scenario: Запуск dev-сервера
- **WHEN** разработчик выполняет `pnpm dev`
- **THEN** сервер стартует без ошибок, а запрос `GET http://localhost:3000/` возвращает HTTP 200

### Requirement: Продакшен-сборка
Проект SHALL собираться командой `pnpm build`, а собранное приложение SHALL запускаться командой `pnpm start`.

#### Scenario: Успешная сборка
- **WHEN** разработчик выполняет `pnpm build` на чистом клоне после установки зависимостей
- **THEN** команда завершается с кодом 0 без ошибок типов и линтера

#### Scenario: Запуск собранного приложения
- **WHEN** после успешной сборки разработчик выполняет `pnpm start`
- **THEN** `GET http://localhost:3000/` возвращает HTTP 200

### Requirement: Строгая проверка типов
Проект SHALL проверять типы в строгом режиме командой `pnpm typecheck`, не создавая артефактов сборки.

#### Scenario: Чистый каркас проходит проверку
- **WHEN** разработчик выполняет `pnpm typecheck`
- **THEN** команда завершается с кодом 0 и не создаёт файлов в репозитории

#### Scenario: Неявный any отклоняется
- **WHEN** в `src/` появляется функция с параметром без типа, тип которого не выводится
- **THEN** `pnpm typecheck` завершается с ненулевым кодом и указывает на этот параметр

### Requirement: Линтинг кода
Проект SHALL проверять исходники правилами линтера для Next.js командой `pnpm lint`; любая ошибка линтера SHALL давать ненулевой код выхода.

#### Scenario: Чистый каркас проходит линтер
- **WHEN** разработчик выполняет `pnpm lint`
- **THEN** команда завершается с кодом 0 без ошибок

#### Scenario: Нарушение правила ломает линт
- **WHEN** в `src/app` используется `<img>` вместо оптимизированного компонента изображения
- **THEN** `pnpm lint` сообщает о нарушении

### Requirement: Единое форматирование
Проект SHALL предоставлять команды `pnpm format` (переформатировать файлы) и `pnpm format:check` (проверить без изменений). Правила форматирования MUST NOT конфликтовать с правилами линтера.

#### Scenario: Проверка форматирования
- **WHEN** разработчик выполняет `pnpm format:check` на каркасе
- **THEN** команда завершается с кодом 0

#### Scenario: Отформатированный код проходит линтер
- **WHEN** разработчик выполняет `pnpm format`, а затем `pnpm lint`
- **THEN** линтер не сообщает об ошибках, связанных с форматированием

### Requirement: Абсолютные импорты
Модули в `src/` SHALL импортироваться через префикс `@/`, который соответствует каталогу `src/`, одинаково при проверке типов, линтинге и сборке.

#### Scenario: Импорт через алиас
- **WHEN** модуль импортирует `@/lib/<module>`, и файл `src/lib/<module>.ts` существует
- **THEN** `pnpm typecheck` и `pnpm build` завершаются успешно

### Requirement: Структура исходников
Репозиторий SHALL содержать каталоги `src/app` (маршруты), `src/components` (UI-компоненты), `src/lib` (утилиты и серверная логика) и `src/data` (статический контент), отслеживаемые git.

#### Scenario: Каталоги присутствуют в чистом клоне
- **WHEN** разработчик клонирует репозиторий
- **THEN** все четыре каталога существуют, даже если в них ещё нет кода

### Requirement: Лицензия
Репозиторий SHALL содержать в корне файл `LICENSE` с текстом лицензии MIT, в котором указаны год и правообладатель.

#### Scenario: Лицензия доступна
- **WHEN** пользователь открывает корень репозитория
- **THEN** файл `LICENSE` содержит текст MIT License

### Requirement: Шаблон переменных окружения
Репозиторий SHALL содержать файл `.env.example` с перечнем переменных окружения и комментариями без реальных значений. Файлы с реальными значениями (`.env`, `.env.local`) MUST NOT попадать в git.

#### Scenario: Шаблон в репозитории, секреты — нет
- **WHEN** разработчик создаёт `.env.local` и выполняет `git status`
- **THEN** `.env.example` отслеживается git, а `.env.local` игнорируется

#### Scenario: Без переменных окружения каркас работает
- **WHEN** ни один `.env*` файл, кроме `.env.example`, не создан
- **THEN** `pnpm build` и `pnpm dev` выполняются без ошибок

### Requirement: Автоматическое отслеживание обновлений зависимостей
Репозиторий SHALL содержать конфигурацию Dependabot, которая еженедельно проверяет обновления npm-зависимостей в корне проекта.

#### Scenario: Конфигурация Dependabot валидна
- **WHEN** репозиторий загружен на GitHub
- **THEN** `.github/dependabot.yml` объявляет экосистему `npm`, каталог `/` и интервал `weekly`, и GitHub принимает файл без ошибок конфигурации
