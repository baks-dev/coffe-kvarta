# Design

## Context

Проект находится на стадии разработки MVP и требует наполнения контентом. Необходимо создать структуру данных для продуктов, контактную информацию, тексты и изображения. Проект использует Next.js, TypeScript и Zod.

## Goals / Non-Goals

**Goals:**
- Создать типизированную структуру данных для продуктов с валидацией
- Организовать хранение статического контента (тексты, контакты)
- Подготовить оптимизированные изображения для веб-использования
- Обеспечить валидацию данных при сборке

**Non-Goals:**
- Не создавать API-эндпоинты для доставки данных (данные будут статическими)
- Не реализовывать админ-панель для редактирования контента
- Не настраивать систему кэширования или CDN
- Не реализовывать i18n в рамках этого изменения (вынесено в бэклог)

## Decisions

### 1. Структура данных продуктов

**Decision:** Использовать JSON-файл (`src/data/products.json`) с валидацией через Zod-схему.

**Rationale:**
- JSON прост для чтения и редактирования
- Zod обеспечивает проверку типов при сборке
- Легко расширять новыми продуктами

**Альтернативы:**
- TypeScript-модуль с экспортом массива — также требует коммита для обновления
- База данных — избыточно для статического контента

### 2. Хранение контента сайта

**Decision:** Хранить все данные сайта (включая siteName) в `src/data/site.ts`. `src/lib/site.ts` остаётся тонкой обёрткой для siteUrl (из NEXT_PUBLIC_SITE_URL).

**Rationale:**
- Единый источник данных для бренда ("Кварта") в одном месте
- siteUrl зависит от окружения, остальные данные статичны
- siteName в layout.tsx будет "Кварта" вместо "Coffe Kvarta"

### 3. Хранение изображений

**Decision:** Хранить изображения в `public/images/` в высококачественном исходном формате (JPEG/WebP q90+), размер до ~2000 px. Оптимизацию делает next/image.

**Rationale:**
- Избежание двойного сжатия (не конвертировать исходники в q85 WebP)
- next/image автоматически конвертирует в WebP (по умолчанию) и создаёт srcset
- Высокое качество исходников гарантирует качество финального изображения

**Альтернативы:**
- Использовать CDN — требует дополнительных затрат и настройки
- Хранить в `src/` — требует обработки через сборщик

### 4. Типизация

**Decision:** Использовать Zod-схемы для валидации JSON-файлов (products.json), а для TypeScript-файлов достаточно `satisfies`.

**Rationale:**
- Zod обеспечивает runtime-валидацию при загрузке JSON
- Для статических TypeScript-модулей достаточно проверки типов компилятором
- Избежание избыточности

### 5. Единый источник данных

**Decision:** Цены хранить в `products.json`, условия доставки и самовывоза — в `site.ts`, а тексты в `content.ts` их не повторяют (кроме маркетингового текста подписки).

**Rationale:**
- Избежание рассинхронизации данных и текстов
- Упрощение обновления (изменить в одном месте)

### 6. Типы продуктов

**Decision:** Использовать `z.discriminatedUnion('type', [...])` с отдельными схемами для каждого типа товара.

**Rationale:**
- Позволяет валидировать разные структуры для разных типов
- Предотвращает потерю полей при парсинге
- Типы: coffee (с roastLevel, notes, recommendedFor), drip-pack (без weight), subscription

### 7. Валидация при сборке

**Decision:** Запускать валидацию через `build` скрипт с помощью `tsx` как devDependency. Валидация добавлена в скрипт `build`.

**Rationale:**
- `tsx` умеет запускать TS без компиляции и поддерживает `import ... with { type: 'json' }`
- `build` скрипт гарантирует валидацию при сборке
- `strip-types` не поддерживает `@/` алиасы

### 8. Допущения

**Decision:** Дрип-пакеты без веса (как в ТЗ), самовывоз — только адрес (часы брать из hours), email → `hello@example.com`.

**Rationale:**
- Точное соответствие ТЗ минимизирует риски
- Документирование допущений в README

## Risks / Trade-offs

- **Риск:** Изменения контента требуют рекомпиляции проекта → **Митигация:** Документировать процесс обновления контента; в будущем рассмотреть Headless CMS
- **Риск:** Валидация может быть пропущена при кастомной сборке → **Митигация:** Явно добавить `pnpm validate-data` в скрипт `build`
- **Риск:** Большие изображения могут замедлить загрузку → **Митигация:** next/image с `preload` для hero, указанными размерами и alt-текстами
- **Риск:** Жестко закодированные тексты сложно переводить → **Митигация:** Заложить структуру для будущей i18n (вынесено в бэклог)
